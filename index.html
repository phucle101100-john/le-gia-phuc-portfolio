04 How I ship with AI agents BlockchainWork v2, 2026

No dev team. I collect requests from the business, turn each into a spec with its edge cases and test cases, and direct AI coding agents that build it in parallel. Then I test against the spec and release. Since April 2026 this is how BlockchainWork is being rebuilt from Bubble into an AI-powered v2. The agents work inside guardrails they cannot switch off, and risky steps wait for a human.

1person, from business request to release, test cases included
1sprint to deliver a request (a sprint is 3 working days)
≤2sprints to close the bugs a large scope produces
1

Orchestrator session

Reads the handover notes first, splits work: one session per feature, each under a 1M-token context budget.

2

Code map

A generated map answers “which files must I read?” per table, endpoint or page, instead of reading the whole repo.

3

Feature session → draft

Builds the feature end to end in its own copy of the code, runs lint, type checks and the test cases locally, then opens a draft for review.

4

CI

Drafts get a cheap check; “ready” triggers the full run. Rule checks fail the build if architecture rules are broken.

5

Independent review

A separate agent that did not write the code reviews the diff. The author re-verifies each finding and posts a QC report pinned to the commit SHA.

6

Label gate

The orchestrator re-checks and adds the QC label. Risky areas need a second label that only a human may add.

7

Merge & deploy

Merge only through one exact command pattern. Production database changes are drafted by the agent and run by a person.

Guardrails the agents cannot talk their way around

$ git push origin main
✖ blocked by hook: direct push to a protected branch

Pre-tool-use hooks

Every shell command an agent runs passes through a hook first. It blocks direct pushes to protected branches, merges that skip QC, writes to the production database, reading environment secret files, and any deploy other than the one allowed service. The hooks have their own unit tests in CI.

$ merge --exact-commit <sha>
✔ QC passed for this commit · CI green · up to date

Merge gate

A merge goes through only if the change has the QC label, the latest QC report for its exact head commit says PASS, every CI check is green, and the branch already contains the newest base commit. Changes to migrations, CI, auth or agent config also need the human-only approval label.

rule browser → database? never
rule auth SDK outside adapter? CI red

Decision records + rules checked by machine

Architecture decisions are written down before code. The parts a machine can check are enforced by CI on every change, so a rule cannot quietly drift.

Habits that keep the output honest

  • Evidence levels. Every status line says whether it was measured, reported by a person, or assumed, with a date.
  • One source of truth per topic. Other docs link to it instead of copying, after a copied status once misled a report.
  • v1 is the floor. v2 screens are compared to v1 step by step, including back, cancel and role-switch paths.
  • Human runs production. Agents draft SQL for production; a person runs it after review.
  • Feedback becomes memory. When I correct an agent, the lesson is written to persistent memory so the next session starts with it.
  • No new spend. Agents cannot upgrade plans or create paid resources without approval.

05 A standard lifecycle before full automation my feedback → a mechanism → a measured result

Agents were not handed full autonomy on day one. Each time I caught a problem, the fix had to be a check the machine runs every time, not a promise from the agent. The lifecycle below is what those checks add up to.

  1. Specuser story, every branch listed, v1 as the floor
  2. Budgetcode map picks files; token estimate per session
  3. Buildone session per feature, own copy of the code
  4. Self-testlocal lint, types, tests; agent walks the real flow in a browser
  5. Draftcheap CI while iterating
  6. Full CIrules, tests, dead-code and duplicate report
  7. Reviewindependent agent; QC report pinned to the commit
  8. GateQC label; risky areas need a human label
  9. Releasemerge by exact command; humans run production SQL
  10. Learnmy correction becomes memory, a hook, a rule or a test
↺ every “Learn” feeds the next “Spec”
“CI is eating the build-minutes budget.”

Measured first: usage was close to the monthly quota and CI had been blocked once. Billed minutes ran well above real run time, because every job rounds up and every merge re-ran everything.

Mechanism: drafts run a light check; the full run starts only when a change is marked ready; merging only rebuilds the code map; container images build only when their files change; documentation-only changes run just formatting; the generated code map stopped being committed, so parallel changes stopped conflicting and re-running.

“Why is the main check slow and nobody speeds it up?”

Measured per step: the test runner built a browser DOM for every file and used one thread on a two-core runner.

Fix: plain Node by default, DOM only for component tests. Tests 118.7 s → 60.1 s; the whole job ~305–330 s → 218 s. Two other ideas were measured and dropped because the gain was too small. Rule kept: any job over ~4 minutes gets timed step by step.

beforeafter
“Find dead code and duplicated logic, don’t just add more.”

Mechanism: CI reports unused files and exports (knip), duplicated blocks of 30+ lines (jscpd) and dead Python (vulture) in every full run. The independent reviewer must hunt dead code and duplicate logic by what the code does, not only by name.

Result: cleanup rounds removed unused components and exports, a leftover API skeleton, and a duplicated form block, until knip reported nothing.

“Test it yourself, along the real flow.”

Mechanism: a verify skill makes the agent drive the browser on v1 and v2 side by side, step by step per role, including back, reload and switching flows; public pages are measured at 1440 px and 375 px. The agent asks me only to log in, never to check for it.

Why: a green CI and a 200 response did not catch a missing review block or a wrong “field missing” error; walking the flow did.

“Give me a mechanism, not a promise.”

Mechanism: merge rights went to agents only behind a hook-enforced gate: QC report for the exact commit, CI green, branch up to date, and a human-only label for risky areas. Full autonomy waits until stronger platform-level controls are in place.

06 Sessions, handover and token budget measured from session transcripts, 10 Nov 2026

An agent forgets everything between sessions and slows down as its context fills. So I treat context like a budget and make handover a written artifact, not a chat memory.

What survives a session

  • Handover notes read first by every session: status by requirement, decisions locked, next steps in order, traps already hit.
  • Shared notes folder where sessions leave hand-over notes and large findings instead of pasting them into chat.
  • Persistent memory: one fact per file, including every correction I gave, so the next session starts with it.
  • Decision records and a change log for every architecture or infrastructure decision.
  • The change itself: description, QC report pinned to a commit, CI result.

Budget before assigning

The orchestrator estimates each session: files the code map says to read, plus room for history and test output. Near 1M means split or narrow the scope.

Fewest tokens in total

Default is one session per feature across DB, API, web and tests. Every new session pays a fixed cost to read the rules and shared code, so splitting a 100k job into five is waste.

Rotate long sessions

The orchestrator has run since 14 Oct and compacted its context 13 times. A child session that grows very long finishes its current change, then new work starts in a fresh session.

Every editor and detail view can be linked, bookmarked and reached with the back button.

One admin roleRole-based permissions

Contact data everywherePersonal data behind a permission

Applicant lists show no name, email or phone. Opening a candidate’s personal data needs its own permission and each view is logged.

Scattered historyOne audit log
